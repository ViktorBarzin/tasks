# tasks — v0.5 feature pass (contract delta v1.4)

Wire-contract additions for the SHARED per-List sort mode. v1.3
(`2026-07-05-v0.4-contract-delta.md` §3) deliberately kept the mode
device-local; this pass revises that: the household wants one mode per List
across every device. The custom ORDER already syncs (`X-APPLE-SORT-ORDER`,
v1.3 §1) — this delta syncs the MODE preference too. Frontend `types.ts` and
backend `schemas.py` must match this exactly, same discipline as v1.1–v1.3.

## 0. Storage decision — custom WebDAV dead property (probed live)

The mode lives ON the CalDAV collection itself, as a custom dead property:

- namespace `urn:viktorbarzin:tasks`, name `sort-mode`, values
  `custom` | `priority` | `due`.

Probed against the real Nextcloud (sabre) on 2026-07-04 with a throwaway
calendar (`probe-sortmode-x9q4`, created via MKCALENDAR, purged afterwards
with `X-NC-CalDAV-No-Trashbin: 1`):

- PROPPATCH of the custom prop → 207 with a `200 OK` propstat (accepted);
- PROPFIND Depth:0 on the collection AND Depth:1 from the calendar home (the
  exact shape `list_task_lists` uses) both return the value;
- the prop SURVIVES unrelated mutations (displayname PROPPATCH, VTODO PUT);
- overwriting the value round-trips (`priority` → `due`);
- unset reads as an empty element under a `404 Not Found` propstat — the same
  shape as an unset `calendar-order`, so the existing parse pattern applies.

The Postgres fallback (`user_list_prefs` table) is therefore NOT built. Note
the property is per-List, not per-(user, List): Lists are single-owner
(CONTEXT.md) and the household explicitly wants the mode shared, so the
collection is the right home. A value written by a foreign client that is not
one of the three modes is read as unset (`null`), never echoed.

## 1. `TaskList.sort_mode` (sync payload)

`TaskList` gains `sort_mode: 'custom' | 'priority' | 'due' | null`:

- Read from the collection's `{urn:viktorbarzin:tasks}sort-mode` dead
  property, fetched by the same Depth:1 PROPFIND that already fetches
  `displayname` + `calendar-order`. Missing/empty/unrecognized ⇒ `null`.
  List tombstones carry `null`.
- `null` means "server has no stored preference": the client falls back to
  its own device-local value (see §3), defaulting to `custom`.
- Lists ship whole in every sync response (full and delta, v1.2 §1), so a
  mode change made on one device propagates to the rest on their next cycle
  without any sync-token involvement.

## 2. New op kind `list_set_sort_mode`

```
{op_id, kind: "list_set_sort_mode", list_id, sort_mode: "custom"|"priority"|"due"}
```

- Server: PROPPATCH the `{urn:viktorbarzin:tasks}sort-mode` property on the
  collection (same machinery as `list_reorder`'s `calendar-order`).
- Idempotency: a replayed `op_id` answers `duplicate` from the journal; a
  re-send with a fresh `op_id` PROPPATCHes the same value again — same end
  state, `applied` (no-op).
- `sort_mode` must be exactly one of the three strings; missing/other types/
  other strings ⇒ per-op `error` (batch continues). Setting the mode on a
  List that no longer exists ⇒ per-op `error` (same as `list_reorder`).

## 3. Client semantics — server first, device-local as fallback only

- Changing the mode in the Sort By picker emits ONE `list_set_sort_mode` op
  (durable queue + optimistic Replica apply, like every mutation) — the fold
  and the cold-launch rebase then keep it visible mid-sync/offline for free.
- The screen's effective mode is `TaskList.sort_mode ?? device-local meta ??
  'custom'`. The pre-v0.5 IndexedDB meta (`sort_mode:<list_id>`) is now ONLY
  a fallback while the server value is `null`; once a server value exists it
  always wins.
- There is deliberately NO auto-migration push: an existing device-local mode
  is never uploaded by itself (a device that merely opens a List must not
  overwrite the household's choice with its own stale leftover). The first
  user-initiated change from the picker is what lands the mode server-side;
  the meta copy is still written on change, as the fallback cache.
- IndexedDB rows persisted by pre-v0.5 builds lack the `sort_mode` key
  entirely; readers treat that exactly like `null` (the `??` fallback), so no
  local schema migration is needed.
