# tasks — v0.2 feature pass (contract delta v1.2)

Wire-contract additions for the v0.2 features (list reorder, priority/description at
creation). Frontend `types.ts` and backend `schemas.py` must match this exactly, same
discipline as the v1.1 pass (`2026-07-03-review-fixes-contract-delta.md`).

## 1. `TaskList.order` (sync payload)

`TaskList` gains `order: int | null`:

- Read from the CalDAV collection's `calendar-order` property (Apple namespace
  `http://apple.com/ns/ical/`), fetched by the same Depth:1 PROPFIND that already
  fetches `displayname`. Missing/empty/unparseable ⇒ `null`. List tombstones carry
  `null`.
- Client Home ordering: sort by `(order ?? MAX_SAFE_INTEGER, name)` — unordered Lists
  sink below ordered ones, alphabetical within ties. `sortedLists` feeds Home, the All
  view grouping and the TaskSheet List picker, so the order is consistent app-wide.
- Lists ship whole in every sync response (full and delta), so an order change
  propagates on the next cycle without any sync-token involvement.

## 2. New op kind `list_reorder`

```
{op_id, kind: "list_reorder", list_id, order: int}
```

- Server: PROPPATCH `calendar-order` (Apple ns) on the collection.
- Idempotency: a replayed `op_id` answers `duplicate` from the journal; a re-send with a
  fresh `op_id` PROPPATCHes the same value again — same end state, `applied` (no-op).
- `order` must be an integer (booleans rejected); missing/invalid ⇒ per-op `error`.
  Reordering a List that no longer exists ⇒ per-op `error` (same as `list_rename`).
- Client: entering reorder mode and dropping a row assigns `order = index` to the new
  visual order and emits ONE `list_reorder` op per List whose stored `order` differs
  (first-ever reorder therefore emits one per List — they all start `null`). Optimistic
  fold updates `order` locally; the server copy arrives with the next sync.

## 3. Creation carries the full field set (no wire change — verified + pinned)

`task_create` already carries the complete `TaskFields` (`title`, `notes`, `due`,
`due_has_time`, `priority`); the backend's `build_vtodo` honors all of them on create
(PRIORITY written for 1/5/9, omitted for 0; DUE as DATE or DATE-TIME per
`due_has_time`; DESCRIPTION only when non-empty). This pass adds tests pinning that,
plus the two UI entry points that now exercise it:

- Quick-add row gains a compact priority control (None/!/!!/!!! — TaskRow's marks).
- Quick-add gains an expand affordance opening TaskSheet in CREATE mode (title
  prefilled from the draft, plus notes, due+time, priority, List picker); Add emits the
  single `task_create` op with all fields, exactly as before.
