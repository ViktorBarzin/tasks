# tasks — v0.4 feature pass (contract delta v1.3)

Wire-contract additions for per-List task sorting (Custom / Priority / Due Date).
Frontend `types.ts` and backend `schemas.py` must match this exactly, same discipline
as the v1.1 (`2026-07-03-review-fixes-contract-delta.md`) and v1.2
(`2026-07-04-v0.2-contract-delta.md`) passes.

## 1. `Task.sort_order` (sync payload)

`Task` gains `sort_order: int | null`:

- Maps 1:1 to the VTODO `X-APPLE-SORT-ORDER` property — Apple's native manual-order
  prop, an integer (any sign, any magnitude; Apple-era values are ~epoch-2001 seconds).
- Read: missing/empty/unparseable ⇒ `null`. Tasks written by Apple in the CalDAV-era
  already carry it — honor the stored value as the Task's Custom position.
- Write: parse-modify-serialize like every other property. Setting an integer rewrites
  exactly the `X-APPLE-SORT-ORDER` line; `null` removes it; an untouched Task keeps it
  **byte-identically** (golden-file preservation applies).
- Task tombstones carry `sort_order: null`.

## 2. `sort_order` joins the mutable task field set (no new op kind)

`sort_order` becomes part of `TaskFields` (`title`, `notes`, `due`, `due_has_time`,
`priority`, `sort_order`):

- `task_update` accepts `sort_order: int | null` — present ⇒ set (or clear on `null`),
  absent ⇒ untouched, exactly like every other field.
- `task_create` carries it like the rest of the field set; `null` ⇒ no property written.
- Validation is per-op: booleans and non-integers are a per-op `error` (batch continues),
  mirroring `priority`.

## 3. Sort modes (client-only; no wire change)

Per-List, device-local preference persisted in IndexedDB `meta` under
`sort_mode:<list_id>` — deliberately NOT synced (each device keeps its own view).
Modes, applied to the OPEN section only (the Completed section keeps its existing
due→priority→title order):

- `custom` (default): `sort_order` asc with `null`s last, then title (base-sensitivity),
  then uid — a total, stable order.
- `priority`: High(1) → Medium(5) → Low(9) → None(0); ties by due asc `null`s-last
  (datetime-aware — all-day before timed within a day), then title, then uid.
- `due`: due asc `null`s-last (datetime-aware), ties by priority rank, then title, then uid.

Sorting is a pure view over the Replica — optimistic ops and sync folds re-sort
naturally, nothing is stored per-row beyond `sort_order` itself.

## 4. Custom-order maintenance (spacing discipline)

- Keys are spaced by a gap of **1024**. A drop between two neighbors takes the integer
  midpoint; when the local gap is exhausted (< 2), only the necessary following
  neighbors are re-spaced — the emitted `task_update` set stays MINIMAL (only rows
  whose `sort_order` actually changes, verified by tests).
- Dropping after the `null` suffix (never-ordered rows) first materializes keys for the
  `null` rows that must precede the moved one (+1024 steps), keeping everything else `null`.
- Quick-add in a List appends at the bottom of the open section:
  `sort_order = max(open concrete keys) + 1024` (`1024` for a List with none). The
  client computes this at `task_create` time for every creation path.
