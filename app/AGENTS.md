# tasks, TypeScript build (app/)

> [!WARNING]
> TanStack Start is NOT Next.js. There is no `getServerSideProps`, no
> `"use server"` / `"use client"` directive, no App Router (`app/page.tsx`,
> `layout.tsx`, `route.ts`), no `next/*` import and no React Server Actions.
> Data loads in route `loader`s and server functions (`createServerFn`);
> HTTP endpoints are server routes (`createFileRoute(...)({ server: { handlers } })`).
> If you catch yourself writing a Next.js pattern, load the skills below first.

This directory is the TypeScript port of `tasks`, built on the default app
stack in `~/code/docs/adr/0001-default-app-stack.md` (read its Pilot section).
The live app is still the FastAPI backend in `../backend` and the SvelteKit PWA
in `../frontend`; they stay untouched until cutover. Work happens on
`wizard/ts-*` branches. Never merge into `master`: CI deploys `master` to the
live app (`.github/workflows/build.yml`, `.woodpecker/deploy.yml`).

## Load the TanStack skills before you write Start or Router code

TanStack ships agent skills inside its npm packages (TanStack Intent): each
package's tarball has a `skills/` directory of `SKILL.md` files written for
the installed version, e.g.
`node_modules/@tanstack/start-client-core/skills/start-core/server-functions/SKILL.md`.
`package.json` → `intent.skills` lists the packages whose skills we trust.

```sh
bun run intent list                                   # what is available
bun run intent load @tanstack/start-client-core#start-core/server-routes
```

Use `bun run intent`, not `bunx intent`: `@tanstack/devtools` also ships an
`intent` binary, which shadows Intent's in `node_modules/.bin`.

## Conventions

### Server-only code lives in `*.server.ts`

Everything that touches the database, CalDAV, crypto, secrets or Bun's
built-ins lives under `src/server/` in files named `*.server.ts`. Import
those modules only from:

- server route handlers (`src/routes/**`, inside `server.handlers`),
- server function handlers (inside `.handler(...)`),
- other `*.server.ts` modules, `src/start.ts` middleware `.server(...)` bodies,
  and `src/entrypoints/*`.

Never import them from a component, a hook, `src/shared/`, or a plain helper
module that a component imports. Start strips server-function and
server-route bodies from the client bundle, but a plain exported helper that
touches the database, sitting in a module the client imports, drags the
Postgres driver into the browser bundle. `vite build`, `tsc` and `curl` all
pass; only a real browser shows `Buffer is not defined` on hydration and every
button silently stops working. After adding server code, run
`bun run test:e2e` (a real Chromium) before calling it done.

There is no lint guard for this (Viktor declined a mandatory one); keep the
convention by hand.

### Server functions vs server routes

- Server functions (`createServerFn`) are internal RPC for this app's own UI.
  They are served at `/_serverFn/<hash>` and speak seroval, so CLIs, agents and
  Home Assistant cannot call them.
- Anything a non-browser client calls is a server route under `/api` with a
  zod schema. The JSON contract the existing PWA uses is in
  `src/shared/contract.ts` and must stay byte-compatible.
- The validator method in Start 1.169 is `.validator()`, not
  `.inputValidator()` (older docs and model memory use the latter).
- `src/routeTree.gen.ts` is generated by `vite build` / `vite dev` and is
  committed. `tsr generate` writes a different file (no Start `Register`
  config block); do not use it.

### Layout

```
src/
  routes/            file routes; /api/* and /healthz, /metrics are server routes;
                     UI routes: index (Home), list.$id, view.$view (all ssr: false)
  components/        React screens and pieces, tasks.css (the iOS look), shadcn/ui
                     in components/ui
  client/            browser-only logic copied from the Svelte build: db (IndexedDB
                     Replica + Op Queue), replica, sync, ops, actions, views, sort,
                     dates, api, signin/relogin, realtime (SSE), ui/ gestures,
                     sw/service-worker.ts; store.ts is a small svelte/store stand-in
  shared/            code for both sides: contract.ts (wire types + zod),
                     replica-contract.ts (frozen IndexedDB layout)
  server/            server-only, every file *.server.ts
    account/         /api/me, /api/onboard, per-user CalDAV engine
    auth/            identity: session (Better Auth), bearer tokens, CSRF
    caldav/          engine (DAV client), ics (VTODO mapping), recurrence
    crypto/          Fernet, byte-compatible with Python's cryptography
    db/              Drizzle schema, pool, migrations, Connected Accounts
    http/            error envelope, /api handler plumbing
    ops/  sync/      POST /api/ops, GET /api/sync, sync cursor
    realtime/        NOTIFY listener, SSE hub, notify helpers
  entrypoints/       bundled with `bun build --target bun` (migrate)
  start.ts           global request middleware (metrics, access log)
e2e/                 Playwright, against the built server (sw/: live service worker)
drizzle/             migrations; 0000_baseline.sql was pulled from Alembic's schema
```

### The UI is client-only, served as one shell

Every screen renders from the IndexedDB Replica, never from the server. The
SSR environment is built with `TSS_SHELL=true` (vite.config.ts), Start's SPA
flag: the server answers every page with the same shell (the root route and
AppGate's boot spinner), and the service worker precaches `/` and serves it
for every navigation, so a deep link cold-starts offline. Do not add loaders
or server rendering to UI routes; data comes from `src/client/`.

Frozen for the cutover (ADR-0001, Pilot / Client continuity): the IndexedDB
name, version and stores (`src/shared/replica-contract.ts`), the op wire
format, the worker URL `/service-worker.js` and the web manifest URL. The
React build replaces the Svelte build's worker in place and drains the ops it
queued; `e2e/sw/cutover.spec.ts` checks exactly that.

- The PWA is vite-plugin-pwa (injectManifest, `src/client/sw/`), run in the
  client build only: per-environment it would rewrite the worker after Nitro
  recorded its size, which truncates it when served.
- Gesture engines in `src/client/ui/` are DOM actions in the Svelte `use:`
  shape, attached with `useAction` (`src/components/useAction.ts`). A drop
  commits inside React's `flushSync`, so the reorder and the transform reset
  paint as one frame.
- An expired session is a 401 `unauthorized` envelope (`AuthWallError`); a
  401 `nextcloud_unauthorized` is the reconnect banner. Sign-in opens
  `/api/signin` in a popup; the fallback navigates to
  `/api/signin?return_to=<path>` after checking the server is reachable.
- `/api/events` (SSE): `poke` from another device, `resync`, and every
  (re)connect run the normal sync cycle.

Contract stubs throw `NotImplementedError` (`src/server/not-implemented.server.ts`),
which /api routes answer as `501 not_implemented`. Each stub's doc comment
names the Python module it ports and the behaviour to keep.

## Commands

All commands use Bun 1.4.3 (`packageManager` in package.json). The devvm's
`~/.bun/bin/bun` may be older until the playbook installs 1.4.3; older Bun
cannot read this `bun.lock`.

```sh
bun install --frozen-lockfile
bun run check        # biome
bun run typecheck    # tsc --noEmit
bun run test         # bun test, src/ only
bun run build        # vite build + bundled entrypoints into .output/
bun run test:e2e     # Playwright against the built server (run build first)
bun run start        # serve .output on $HOST:$PORT
```

## Tests

- `bun test` with happy-dom and Testing Library. `bunfig.toml` sets
  `[test] root = "src"` and preloads `src/test/happydom.ts` (DOM globals,
  keeping Bun's fetch/Request/Response) and `src/test/setup.ts` (jest-dom
  matchers, cleanup, quiet logs). The test script sets `NODE_ENV=test`.
- Tests sit next to the code: `foo.server.ts` → `foo.server.test.ts`,
  `Thing.tsx` → `Thing.test.tsx`.
- Port the Python tests (`../backend/tests`) as the correctness oracle.
  `hypothesis` property tests become `fast-check` properties;
  `fake_caldav.py` becomes an in-memory `CalDAVTransport`.
- Server functions need Start's request context, so test them over HTTP
  against the built server, not by importing them.
- Database tests run when `TEST_DATABASE_URL` is set (a role that can create
  databases); each test makes and drops its own database. See
  `src/server/db/db.server.test.ts` for a one-line Postgres container recipe.
- The live Python Fernet check runs when `TASKS_FERNET_PYTHON` points at a
  Python with `cryptography` (e.g. `../backend/.venv/bin/python`).
- Playwright lives in `e2e/`, outside `bun test`'s root. For iOS Safari use
  `homelab ios`, not an emulated viewport. Projects: `mobile-chromium-touch`
  (`*-touch` specs, CDP touch), `desktop-chromium-mouse` (`*-mouse`, smoke),
  and `pwa` (`e2e/sw/`, a live service worker behind the per-test stub origin
  in `e2e/fixtures/pwa-server.ts`, with an OIDC stand-in). Gesture specs stub
  /api with `page.route`; a service worker's requests cannot be stubbed that
  way, hence the stub origin.
- The cutover spec serves the Svelte build from `../frontend/build`;
  `e2e/global-setup.ts` builds it with npm when it is missing.

## Database

- Drizzle on Bun's SQL client (`drizzle-orm/bun-sql`). The pool holds at most
  5 connections; the migrate entrypoint uses 1.
- `DATABASE_URL` has no password in production; the password is read from
  `DATABASE_PASSWORD_FILE` each time a connection opens, so Vault rotation
  does not break new connections.
- The schema matches Alembic's tables exactly (`bun run db:generate` must say
  "No schema changes"). `enc_app_password` is a hand-written `bytea` custom
  type holding the Fernet token's ASCII bytes; `updated_at` uses `$onUpdate`.
- Migrations stay additive while the Python image is a rollback target: it
  runs `alembic upgrade head` on every start. drizzle-kit ignores
  `alembic_version` (`tablesFilter`).
- The baseline is recorded as applied, not run, on a database Alembic
  manages: `markBaselineIfLegacy` in `src/server/db/migrate.server.ts` inserts
  the baseline's hash and timestamp into `drizzle.__drizzle_migrations` when
  `public.alembic_version` exists and Drizzle has no rows yet. It runs under
  the same `pg_advisory_lock` as the migrator. A fresh database runs the
  baseline normally.

## Configuration

| Env | Meaning |
|---|---|
| `DATABASE_URL`, `DATABASE_PASSWORD_FILE` | Postgres; see above |
| `MIGRATIONS_DIR` | migrate entrypoint; `/app/drizzle` in the image |
| `TASKS_FERNET_KEY` | encrypts Nextcloud app passwords (same key as the Python app) |
| `TASKS_CALDAV_BASE_URL` | Nextcloud DAV root |
| `TASKS_LOCAL_TZ` | all-day recurrence zone, default `Europe/Sofia` |
| `TASKS_ACCOUNT_KEY_CLAIM` | `preferred_username` (default) or `sub` after the cutover mapping |
| `PUBLIC_ORIGINS` | exact origins for the CSRF check |
| `DEV_USER` | dev and test identity; ignored when `NODE_ENV=production` |
| `LOG_LEVEL` | `DEBUG`, `INFO` (default), `WARNING`, `ERROR` |
| `HOST`, `PORT` | listen address; the image uses `0.0.0.0:3000` |

Logs are JSON lines on stderr with `ts`, `level`, `logger`, `msg` and extras,
the same shape as the Python app. `/metrics` (prom-client) and `/healthz` are
on the pod port.

## Image

`Dockerfile` builds on `oven/bun:1.4.3` and runs on
`oven/bun:1.4.3-distroless` as `USER 10001:10001`, copying only `.output` and
`drizzle/`. The server is the default command; run the migrate entrypoint from
